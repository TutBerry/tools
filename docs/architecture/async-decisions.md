# Решения по асинхронному взаимодействию TutBerry

## Брокер

Выбран RabbitMQ, а не Kafka: для уведомлений и сброса кеша нужны независимые очереди задач, подтверждения и DLQ, а не повторное чтение истории событий. Решение пересматривается при появлении потребителей исторических данных.

## Доставка и дедупликация

Для опубликованных сообщений используется модель at-least-once: долговечные очереди, persistent-сообщения, publisher confirms и ручное подтверждение после обработки. Повторы возможны. Valkey хранит processed:* на 24 часа. Аренда на 60 секунд захватывается атомарно через SET NX EX; Lua проверяет токен владельца при завершении и освобождении. При отказе аренда освобождается либо истекает. Чужая аренда не расходует попытку. Строгая гарантия exactly-once отсутствует: сбой после SMTP, но до отметки, допускает повторное письмо. Максимальная длительность обработки пока не ограничена общим таймаутом.

## Потребители

| Очередь | События | Дедупликация |
|---|---|---|
| booking.notifications | booking.* | Valkey |
| booking.cache | booking.created, booking.cancelled, booking.withdrawn | Удаление кеша идемпотентно |

Один worker, два канала Pika. Блокирующая обработка может задерживать второй канал; при росте нагрузки потребителей следует разделить. Создание заявки вызывает письмо о создании, снятие — письмо с причиной, отмена пропускается. Сейчас API публикует только booking.created; события отмены и снятия определены, но соответствующие API-сценарии не подключены. Поиск email использует существующее преобразование UUID пользователя и пока требует перебора записей.

## Транзакции

AfterCommitEventBus использует Django transaction.on_commit. При откате событие не публикуется. Брокер подключается при публикации, а не при запуске API. При отказе брокера бронь сохраняется, ошибка журналируется. Бронь важнее оповещения. Между фиксацией и публикацией событие может потеряться; transactional outbox отложен до ЛР 7. Таймауты подключения Pika ограничены, но не являются общим дедлайном всей публикации.

## Кеш рядом

Источник истины — PostgreSQL. Valkey хранит результаты поиска 5 секунд; ключ учитывает даты, фильтры и limit. Событие инвалидирует все ключи listings:* через SCAN и DELETE. Это уточняет подход ADR-0005 без изменения прежних ADR: сброс асинхронный, не часть сценария бронирования. Цена — кратковременная устарелость; гонка чтения и инвалидирования может оставить результат до истечения TTL. Задержка не измерена. При недоступности кеша запрос идёт в PostgreSQL; при недоступности хранилища дедупликации обработчик повторяет попытку. AOF включён для сохранения отметок. HTTP-идемпотентность не переносится в Valkey.

## Повторы

Три попытки по умолчанию, полный jitter с потолками 1 и 2 секунды, общий потолок задержки 30 секунд. Чужая аренда проверяется повторно без увеличения счётчика. Временные ошибки повторяются, постоянные и неизвестные исключения направляются в DLQ. Повтор публикуется в собственную очередь, не в общий exchange. Исходное сообщение подтверждается после подтверждённой публикации копии. DLQ сохраняет исходное тело, идентификатор, вид события, число попыток, причину и время ошибки. Задержка внутри callback занимает обработчик.

## Доступность и согласованность

| Компонент | Решение |
|---|---|
| PostgreSQL | Согласованность; без базы бронь не создаётся. HTTP 503 требует проверки и при необходимости доработки. |
| Valkey (кеш) | Доступность; поиск через БД. |
| RabbitMQ | Доступность бронирования; уведомление может потеряться. |
| Valkey (дедупликация) | Повтор вместо обработки без защиты. |

API ждёт готовности БД и только запуска кеша и брокера. Worker ждёт готовности БД, кеша и брокера.

## Границы и проверка

Не реализованы Kafka, transactional outbox, отдельные очереди задержки и строгая exactly-once доставка. SMTP использует учебный Mailpit. Интеграционные проверки, реальное время сброса кеша, восстановление после остановки служб и итоговый CI ещё не подтверждены. Результаты фиксируются после выполнения проверок, а не заранее.
