# Архитектурные диаграммы TutBerry

Все диаграммы представлены в текстовом формате Mermaid. Изменения моделей хранятся в Git вместе с остальной документацией.

## Состав

| Файл | Назначение | Читатель |
|---|---|---|
| `c4/context.mmd` | Участники, границы TutBerry и внешние системы | Заказчик, новый участник проекта |
| `c4/container.mmd` | Запускаемые части системы, технологии и протоколы | Разработчик, специалист по эксплуатации |
| `sequence/create-booking.mmd` | Порядок создания и подтверждения заявки, ошибки и конфликт дат | Разработчик API и тестировщик |
| `data/model.mmd` | Сущности, ключи, атрибуты и кардинальности | Разработчик базы данных |

## Согласование моделей

| Элемент | Основание | Отражение в модели |
|---|---|---|
| Арендатор, владелец, модератор | Персоны и заинтересованные стороны из `docs/requirements.md` | Участники контекстной диаграммы |
| Web UI, Django API, PostgreSQL | `C-01`, ADR-0002, ADR-0003 | Контейнерная диаграмма |
| JWT и проверка прав | ADR-0004, `NFR-03` | Связь Web UI → API и ветка `401` |
| Доступность и конфликт дат | `FR-01`, `FR-04`, `FR-07`, ADR-0005 | Проверка дат в транзакции и ответ `409` |
| Объявление и календарь | `FR-01`, `FR-04`, `FR-06` | `LISTINGS`, `LISTING_AVAILABILITY` |
| Заявка | `FR-07` | `BOOKINGS`, `POST /api/v1/bookings` |
| Оплата и залог | `FR-02`, `FR-03` | `TRANSACTIONS`, `/payments` |
| Споры и отзывы | `FR-05`, `US-12` | Маршруты `/admin/disputes`, `/reviews`; связь с бронированием |

Модули `users`, `catalog`, `bookings`, `payments`, `notifications` и `reviews` из модели предметной области 2Б находятся внутри одного контейнера Django API. Контексты обозначают границы предметной логики, а не отдельные процессы.

В модели данных `docs/architecture/data/model.mmd` используются существующие таблицы проекта. История состояний хранится через статусы, а не удаление бронирований. UUID выступают первичными ключами; email — уникальный естественный ключ. Модель содержит более четырёх сущностей, их атрибуты и кардинальности.

## Границы представления

Диаграмма компонентов C4 не добавляется: предметные модули отражены в ADR-0003 и карте контекстов 2Б. Диаграмма развёртывания относится к следующему этапу. Контейнер C4 обозначает самостоятельную запускаемую часть или хранилище, а не Docker-контейнер.

Брокер и фоновый обработчик на контейнерной диаграмме обозначены как элементы ЛР 6А. Они не входят в принятое решение о модульном монолите как отдельные предметные сервисы. Выбор конкретного брокера не зафиксирован; он не влияет на синхронный сценарий создания заявки.

## Поддержка актуальности

При изменении внешних интеграций обновляется `c4/context.mmd`. При изменении состава запускаемых частей или протоколов обновляется `c4/container.mmd`. При изменении процесса бронирования обновляется `sequence/create-booking.mmd`, а при изменении схемы хранения — `data/model.mmd`. Операции REST синхронизируются с `docs/api/resources.md`.

Для локальной проверки Mermaid используется команда:

```bash
npx --yes @mermaid-js/mermaid-cli -i docs/architecture/c4/context.mmd -o /tmp/tutberry-context.svg
```

Та же проверка выполняется для остальных файлов `.mmd`.
